# Calibration log — offline llama3 (llama3.1:8b) vs Claude reference

Generated by a RAG-grounded offline generator (private companion repo), then corrected to match the
human-authored `spec.md` + the verified `impl_claude.py` reference. This log is the
record of *where the offline model diverged* — the point of the three-model design.

## Headline finding
The offline model (llama3.1:8b, grounded in the local 3GPP RAG) reliably got the
**conformance logic** right — the MUST/MUST NOT conditions and the PASS/FAIL/INCONCLUSIVE
ordering — but consistently failed on **implementation fidelity**: the internal API
contract, the exact 3GPP/tshark field names, and (worst) it **hallucinated the hard
parts** rather than admitting it couldn't do them. This is exactly the failure mode a
spec-correct reference is meant to catch.

## Per-feature corrections

| Feature | llama3 got RIGHT | `[NEEDS CORRECTION]` (what was fixed) |
|---|---|---|
| suci | FAIL-on-`null_scheme_frames>0`; SMC/SMP/SUCI checks | Wrong `VerificationResult()` constructor; wrong field `nas-5gs.mm.suci.protection-scheme-id` → `scheme_id`; `count_msg_type()` called with a bare int; wildcard `suci.*` filter |
| registration | Verdict ordering; metrics on every return (its best draft) | `count_msg_type(tshark,pcap,0x41)` wrong signature; `count(tshark,pcap,0x56)` passed an int as a filter |
| pdu_session | Verdict structure | `count()` called without a tshark path; invented filters `nas.frame`, `gtp.u`, `nas.ue_registered`; broken constructor |
| sib1 | MUST-NOT mismatch → FAIL logic | **Most broken**: assumed `evidence` was a pre-parsed dict; misused `find_tshark()`; hallucinated per-frame PLMN iteration. Rewritten to parse the real cu.conf/du.conf |
| aka | INCONCLUSIVE→FAIL→PASS ordering | **Hallucinated the crypto** — invented `tshark -z crypto,hash,sha256` instead of Milenage; treated `evidence` as a dict. Replaced with the real Milenage + KDF (Annex A.4/A.5) |

## Recurring error classes (across all five)
1. **API contract** — wrong `VerificationResult(...)` constructor / kwargs (would crash before returning).
2. **Field-name fidelity** — plausible-but-wrong tshark fields (`protection-scheme-id`, `gtp.u`, `nas.frame`).
3. **Input model** — assumed `evidence` was a parsed dict instead of a folder path.
4. **Hallucinating the hard part** — faking Milenage and SIB1 parsing rather than implementing them.
5. **Non-determinism** — regenerating the same feature produced materially different code each run (even at temperature 0.1), so no single draft is authoritative.

## Second offline model — mistral:latest (same features, different failures)
Regenerating with mistral produced a *different* set of errors — useful evidence that the
failure modes are model-specific, not a one-off:

| Feature | mistral-specific error |
|---|---|
| suci | Invented a non-existent enum `VerificationResult.Verdict.FAIL`; fabricated filter `ngap.ie.value:0 and ngap.ie.id==128` for null-scheme |
| registration | Invented UDP port filters (`udp.port == 28504`, `44444`) for NGAP/NAS |
| aka | **Hard Python syntax error** (mismatched parens) — the file would not even parse; left `derive_res_xres()` / `find_snn()` as empty stubs "omitted for brevity" (didn't attempt the crypto at all) |
| pdu_session | Invented UDP ports; treated `count_msg_type(...)["count"]` as a dict; invented `VerificationResult.PASS` enum |
| sib1 | Called the tshark path string as a function `tshark('sib1')`; invalid `VerificationResult(inconclusive=...)` kwarg |

New error classes beyond llama3's: **invented enums**, an actual **syntax error** (unparseable),
and **empty stub functions** where the hard work should be (worse than llama3's hallucination —
it didn't even pretend). Same corrections applied; both offline impls now match the reference.

## After calibration
Every corrected `impl_llama3.py` and `impl_mistral.py` runs and agrees with the Claude reference:
- Verified here (no tshark needed): `sib1` → PASS (claude/llama3/mistral all metrics match),
  `aka` → PASS (`res_star_match=True` for all three).
- To verify on-box (need tshark): `suci` → FAIL (null scheme), `registration` → PASS, `pdu_session` → PASS.

Run `python compare/diff_report.py --all` — with all three agreeing, the Claude result freezes
as `golden/<feature>_claude.json`. That is the bottom of the pipeline diagram reached.

## Takeaway for the writeup
A local, spec-grounded model is good enough to draft a conformance check but not to be
*trusted* with one: it is confidently wrong on field names and will fake cryptography.
The value of the pipeline is precisely that the human-authored oracle + the spec-correct
reference catch these — turning an untrustworthy offline draft into a calibrated, trustworthy verifier.
